# 쿠팡 체험단 리뷰 필터 확장 설계

작성일: 2026-09-28
상태: 설계 확정, 구현 계획 대기

---

## 1. 개요

### 한 줄 정의

쿠팡 상품 페이지에서 체험단 제공 리뷰를 걸러내고, 협찬을 제외한 실제 평점을 그 자리에서 보여주는 크롬 확장.

### 문제

쿠팡 리뷰에는 체험단 제공 리뷰가 섞여 있다. 이 리뷰들은 표시광고법에 따라 문구로 표기되지만, 화면에 표시되는 평점에는 그대로 반영된다. 사용자가 보는 4.7점에는 협찬 리뷰가 포함되어 있고, 그것만 빼면 4.1점인 경우가 있다. 사용자는 이 차이를 알 방법이 없다.

### 포트폴리오 목표

이 프로젝트의 본체는 제품이 아니라 분석이다. 목표 직무는 커머스 데이터 분석과 그로스이며, 다음 세 가지를 증명한다.

1. 이벤트 택소노미를 직접 설계하고 계측을 구축했다
2. 퍼널 병목을 찾아 가설을 세우고 A/B로 검증했다
3. 분석 결론이 이 서비스 밖에서도 의미를 가진다

세 번째가 핵심 차별점이다. 이 프로젝트에서 나오는 결론은 다음과 같은 형태다.

> 기본 정렬에서 노출되는 리뷰의 협찬 비중이 최신순보다 유의하게 높았다. 리뷰 신뢰도 문제는 평점이 아니라 노출 구조에서 발생한다.

이는 모든 커머스 회사가 실제로 궁금해하는 질문이며, 면접에서 "저희 서비스에 적용하면"으로 바로 이어진다.

> **2026-09-30 갱신.** 최초 작성 시 예상한 결론은 "체험단 제외 평점 하락폭이 큰 상품에서 구매 의도가 낮다" 였다. 구현 후 실측에서 이 전제가 흔들렸다. 4.4절을 참조한다.

## 2. 범위

### 포함

- 쿠팡 상품 페이지에서 동작하는 크롬 확장 (엣지, 웨일 포함)
- 체험단 리뷰 판별, 숨기기, 평점 재계산
- 인페이지 배너와 사이드 패널 UI
- 확장 소개 및 설치 유도용 랜딩 1페이지
- 앰플리튜드 계측 (랜딩과 확장 양쪽, 신원 연결 포함)

### 제외

- 쿠팡 외 플랫폼
- 서버측 크롤링
- 리뷰 원문의 외부 저장이나 재게시
- 모바일에서의 확장 동작 (랜딩은 모바일 대응)
- 다중 플랫폼 상품 동일성 매칭

### 카테고리 제약 없음

확장은 수집을 하지 않으므로 상품 카테고리를 한정할 필요가 없다. 쿠팡 상품 페이지면 어디서든 동작한다.

## 3. 사용자 경험

### 3.1 설치 여정

```
커뮤니티 게시글
  → 랜딩 페이지 방문
  → 설치 버튼 클릭
  → 크롬 웹스토어
  → 설치 완료
  → 온보딩 페이지 자동 오픈 (예시 상품 링크 제공)
```

실질 클릭 네댓 번. 랜딩 페이지 이후로는 사이트에 다시 올 일이 없다.

### 3.2 사용 여정

설치 이후 사용자는 평소처럼 쿠팡에서 쇼핑한다. 상품 페이지를 열면 확장이 자동으로 작동한다.

```
쿠팡 상품 페이지 열기
  → 리뷰 영역 위에 배너 자동 노출
  → (선택) 배너 클릭으로 사이드 패널 열기
  → 필터 토글, 근거 확인
  → 구매 결정
```

사용자는 쿠팡을 떠나지 않는다. 검색하거나 링크를 복사할 필요가 없다.

### 3.3 UI 구성

**인페이지 배너 (자동 노출)**

리뷰 영역 위에 얇게 삽입된다. 발견을 담당한다.

```
리뷰 1,204개 중 체험단 341개 (28%)
쿠팡 평점 4.7  →  체험단 제외 4.1
[ 체험단 숨기기 ]
```

**사이드 패널 (클릭으로 열림)**

배너 클릭 또는 툴바 아이콘으로 열린다. 상세 내용을 담당한다.

- 체험단 제외 평점
- 체험단 비중 막대
- 별점 분포 비교 (전체 대 체험단 제외)
- 체험단 제외 리뷰 목록

크롬 사이드 패널 API는 사용자 제스처를 요구하므로 페이지 로드만으로 자동으로 열 수 없다. 이 때문에 발견은 인페이지 배너가, 내용은 패널이 담당하는 이원 구조를 택한다.

### 3.4 모바일

확장이 동작하지 않는다. 안드로이드 크롬은 확장을 지원하지 않고, iOS 사파리는 App Store 배포가 필요하며, 쿠팡 앱은 네이티브라 손댈 수 없다.

랜딩 페이지는 모바일에서 완전히 동작하고, 설치 지점에서 핸드오프를 제공한다.

```
"모바일에서는 확장이 동작하지 않습니다.
 PC에서 설치할 링크를 보내드릴까요?"  → 이메일 입력
```

링크에 토큰을 실어 보내고, PC에서 열면 동일 사용자로 식별한다.

## 4. 판별 로직

### 4.1 확정 신호: 접두 앵커 매칭

> **2026-09-29 갱신.** 최초 작성 시에는 쿠팡이 단일 고정 문장을 붙인다고 보고 "정밀도 100%"로 썼다. 구현 중 실제 상품 페이지를 조사한 결과 이 전제가 틀렸다. 아래는 실측에 기반한 판본이다.

쿠팡은 체험단 리뷰에 시스템이 표기 문구를 붙이지만, 문장 끝이 갈린다. 상품 7590830589 한 곳에서만 세 가지 변형이 관측되었다.

```
쿠팡체험단 이벤트로 상품을 무료로 제공 받아 작성한 구매 후기입니다.
쿠팡체험단 이벤트로 상품을 무료 제공받아 작성한 리뷰입니다.
쿠팡체험단 이벤트로 상품을 무료로 제공 받아 작성한 구매후기입니다
```

`무료로 제공 받아` 대 `무료 제공받아`, `구매 후기입니다` 대 `리뷰입니다` 대 `구매후기입니다` 로 나뉜다. 전체 문장을 마커로 쓰면 이 상품의 체험단 리뷰 6건 중 2건만 잡힌다.

따라서 세 변형이 공유하는 **접두를 앵커로 쓴다.**

```
쿠팡체험단 이벤트로 상품을 무료
```

이보다 짧게 자르면 사용자가 체험단을 언급만 한 리뷰를 오탐할 위험이 커지고, 길게 두면 변형을 놓친다. 공백을 모두 제거한 뒤 비교하므로 줄바꿈으로 쪼개진 표기도 잡힌다.

머신러닝이나 휴리스틱은 여전히 필요 없다. 다만 "정형 문자열이라 정밀도 100%"라는 최초 전제는 성립하지 않으며, 마커는 관측에 따라 갱신되는 값으로 다룬다.

판별 패턴은 `core/sponsored.js` 의 `SPONSORED_MARKERS` 상수에만 두고, 매칭 실패율이 급변하면 `Extension Error` 로 감지한다. 새 변형이 발견되면 이 배열에 추가한다.

### 4.2 표기 원칙: 판정이 아니라 근거 제시

리뷰에 "가짜입니다"라고 쓰지 않는다. 다음과 같이 근거만 제시한다.

```
체험단 제공 리뷰
```

이유는 두 가지다. 첫째, 사용자 신뢰는 단정이 아니라 근거에서 나온다. 둘째, 특정 상품이나 리뷰를 단정적으로 규정하면 분쟁 소지가 생긴다.

### 4.3 평점 재계산

```
체험단 제외 평점 = (전체 별점 합 - 체험단 별점 합) / (전체 개수 - 체험단 개수)
```

페이지에 로드된 리뷰만 대상으로 한다. 쿠팡은 리뷰를 페이지네이션으로 제공하므로, 계산 범위를 사용자에게 명시한다.

```
현재 로드된 리뷰 120개 기준
```

전수 집계를 위해 추가 요청을 보내지 않는다. 사용자가 스크롤이나 페이지 이동으로 더 많은 리뷰를 로드하면 재계산한다.

### 4.4 실측 관찰: 정렬에 따른 노출 편향 (2026-09-30)

구현 완료 후 실제 상품 하나(7590830589, 칫솔살균기)에서 정렬만 바꿔 측정했다. 같은 상품, 같은 50건 창이다.

| 페이지 | 최신순 | 베스트순 |
|---|---|---|
| 1 | 0/10 | 5/10 |
| 2 | 0/10 | 9/10 |
| 3 | 0/10 | 5/10 |
| 4 | 0/10 | 1/10 |
| 5 | 0/10 | 0/10 |
| **합계** | **0/50 (0%)** | **20/50 (40%)** |

최신순 상위 50건에는 체험단이 한 건도 없고, 베스트순은 40%다.

**메커니즘.** 리뷰 id를 보면 최신순 50건은 전부 최근(1006400612 이상)이고, 베스트순에 올라온 체험단은 전부 오래된 것(554884409, 614749908, 615925018, 686169416 등)이다. 체험단 캠페인은 과거에 있었고, 그 리뷰들이 그동안 도움돼요를 누적해 베스트순 상단을 차지한다. 쿠팡의 기본 정렬이 베스트순이므로, **쇼핑객이 기본으로 보는 화면은 협찬 비중이 높고 최신 진짜 구매자 리뷰는 한 번 더 클릭해야 나온다.**

**전제 변화.**

| | |
|---|---|
| 최초 가설 | 체험단이 평점을 부풀린다 |
| 실측 | 이 상품은 평점이 5 → 5. 부풀림 없음 |
| 갱신된 가설 | 문제는 평점이 아니라 노출 구조다. 기본 정렬이 오래된 협찬 리뷰를 선택적으로 끌어올린다 |

**한계.** 상품 하나의 관측이다. 과거에만 캠페인을 돌린 상품일 수 있고, 진행 중인 상품이면 최신순에도 체험단이 나온다. 일반화하려면 상품 수십 개에서 같은 대비를 봐야 한다. 이것이 계측이 필요한 이유다.

**계측에 주는 함의.** `rating_delta` 만 보면 이 상품은 "아무 일 없음" 으로 집계된다. 실제 신호는 정렬별 협찬 비중 차이이므로, 이벤트에 **현재 정렬 상태**를 담아야 한다. 6.2절과 6.3절에 반영되어 있다.

**정렬별 첫 페이지 비교.** `Banner Rendered` 에서 `sort_pages_seen = 1` 로 정렬별 첫 페이지를 고르고 `page_first_review_id` 로 같은 페이지 재방문을 중복 제거한다. `pages_seen` 은 조회 횟수라 정렬을 바꿔도 계속 늘어나므로 이 비교에 쓰지 않는다.

**제품에 주는 함의(미결정).** 협찬을 걸러 주는 것보다 "최신순으로 보세요"가 사용자에게 더 큰 가치일 수 있다. 클릭 한 번이면 되기 때문이다. 다만 상품 하나의 관측으로 제품 방향을 바꾸지 않는다. 계측 데이터가 쌓인 뒤 판단한다.

## 5. 기술 구조

### 5.1 확장 구성

| 구성 요소 | 역할 |
|---|---|
| content script | 쿠팡 상품 페이지의 리뷰 DOM 파싱, 배너 삽입, 필터 적용 |
| side panel | 통계와 필터링된 리뷰 목록 표시 |
| background service worker | 앰플리튜드 이벤트 전송, 신원 관리 |
| storage | 익명 ID, 실험 배정값, 사용자 설정 |

이벤트 전송을 백그라운드에서 수행하는 것이 중요하다. 콘텐츠 스크립트에서 직접 보내면 쿠팡 페이지의 보안 정책에 막힐 수 있다.

### 5.2 권한 최소화

`host_permissions`를 쿠팡 도메인으로 한정한다. 전체 도메인 권한을 요구하지 않는다. 웹스토어 심사가 빨라지고 사용자 신뢰도 올라간다.

### 5.3 랜딩 페이지

정적 1페이지. 구성은 다음과 같다.

- 문제 제기와 데모 이미지
- 설치 버튼
- 모바일 방문자용 핸드오프 폼
- 개인정보 처리 안내

랭킹표나 상품 데이터베이스는 만들지 않는다. 수집 노동과 저작권 리스크를 모두 피한다.

### 5.4 데이터 저장 정책

리뷰 원문은 어떤 형태로도 서버에 저장하지 않는다. 확장은 사용자 브라우저 안에서만 동작하며, 서버로 나가는 것은 앰플리튜드 이벤트뿐이다.

## 6. 계측 설계

### 6.1 신원 연결

> 11.5절(2026-10-02 개정)이 이 절의 해법을 대체한다.

랜딩과 확장은 별개 실행 환경이라 그대로 두면 같은 사람이 둘로 집계된다. 그러면 획득 퍼널이 끊긴다.

**해법**

설치 직후 확장이 랜딩 도메인의 `/installed` 페이지를 연다. 이 페이지는 랜딩과 같은 출처이므로 랜딩의 `device_id`를 읽을 수 있다. 콘텐츠 스크립트가 그 값을 받아 확장 저장소에 저장하고, 이후 모든 확장 이벤트는 그 `device_id`로 전송한다.

```
랜딩 방문 (device_id: abc123)
  → 설치 → 확장이 /installed 자동 오픈
  → 콘텐츠 스크립트가 abc123 수신, chrome.storage 저장
  → 이후 확장 이벤트 전부 abc123
```

`/installed` 페이지가 온보딩 화면 역할도 겸한다.

**크로스 디바이스**

핸드오프 링크에 토큰을 실어 보낸다. PC에서 열면 같은 `user_id`로 식별한다. `user_id`는 이메일 해시값을 쓰고 원문 이메일은 앰플리튜드로 보내지 않는다.

### 6.2 공통 프로퍼티

모든 이벤트에 자동 첨부한다.

| 프로퍼티 | 값 | 목적 |
|---|---|---|
| `surface` | `site` / `extension` | 모든 분석의 1차 분할 축 |
| `platform` | `desktop` / `mobile` | 모바일은 랜딩에만 존재 |
| `is_extension_installed` | boolean | 랜딩 방문자를 설치자와 미설치자로 분리 |
| `entry_source` | 정규화 유입원 | 커뮤니티별 성과 비교 |
| `exp_default_filter` | `on` / `off` | 실험 배정 |
| `exp_banner_copy` | variant | 실험 배정 |
| `app_version` | 버전 문자열 | 셀렉터 깨짐 추적 |
| `review_sort` | `best` / `latest` / `unknown` | **4.4절의 핵심 축.** 정렬별 협찬 비중 비교 |
| `product_id` | 쿠팡 상품 번호(11.3절에 따라 `product_key` 로 전송) | 상품별 분석, 4.4절 일반화 |

`app_version` 0.2.0 미만의 이벤트는 `review_sort` 가 항상 `best` 로 기록됐으므로(정렬 버튼 활성 판정 버그) 정렬 분석에서 제외한다.

`product_id`는 확장의 콘텐츠 스크립트가 보내는 이벤트에만 붙는다. 사이드 패널 이벤트는 상품을 알지 못하므로 싣지 않는다. 11.3절에 따라 상품 번호 원문은 보내지 않고 `product_key` 로 바꿔 보낸다.

`is_extension_installed`는 확장이 페이지에 마커를 심어 랜딩에서 감지한다.

### 6.4 확장이어야만 얻는 데이터

`Purchase Intent Clicked`가 이 설계의 핵심이다. 확장은 쿠팡 페이지 안에서 동작하므로 사용자의 실제 장바구니, 바로구매 클릭을 관측할 수 있다.

외부 링크 클릭 같은 약한 프록시가 아니라 진짜 구매 의도 행동을 본다. 이 차이가 분석의 질을 결정한다.

### 6.5 북극성 지표

**주간 필터 활성 세션 수**

필터가 적용된 상태로 리뷰를 본 세션의 주간 합계. 설치 수는 허영 지표라 쓰지 않는다. 사용자 수와 사용 빈도를 한 숫자에 담고, 전달된 가치와 직결된다.

### 6.6 퍼널

앰플리튜드에 다음 네 개를 만들어 둔다.

| 퍼널 | 구간 |
|---|---|
| F1 획득 | `Landing Viewed` → `Install CTA Clicked` → `Store Redirected` → `Extension Installed` |
| F2 활성화 | `Extension Installed` → `Onboarding Viewed` → `Banner Rendered` → `Panel Opened` |
| F3 가치 | `Banner Rendered` → `Panel Opened` → `Filter Toggled` → `Purchase Intent Clicked` |
| F4 리텐션 | 주차별 `Banner Rendered` 재발생 |

F2가 최대 병목으로 예상된다. 설치하고 한 번도 쓰지 않는 사용자가 가장 많이 새는 구간이며, 실무에서도 가장 어려운 지점이다.

### 6.7 가드레일

- `Extension Error` 발생률
- `Extension Removed` 비율

개선을 밀다가 이 둘이 오르면 방향이 틀린 것이다.

### 6.8 A/B 실험

배정 로직과 `exp_*` 프로퍼티를 구현 시점에 함께 넣는다. 나중에 붙일 수 없다.

| ID | 내용 | 배정 | 비교 지표 |
|---|---|---|---|
| `exp_default_filter` | 필터 기본값 ON 대 OFF | 50 대 50 | 필터 활성 세션 비율, 구매 의도 클릭률 |
| `exp_banner_copy` | 숫자 강조 (4.7 → 4.1) 대 비중 강조 (28%가 체험단) | 50 대 50 | 패널 열기율, 필터 토글률 |
| `exp_install_cta` | CTA 위치 3종 | 균등 | 설치 완료율 |
| `exp_onboarding_example` | 온보딩 예시 링크 유무 | 50 대 50 | 첫 작동률 |

`exp_default_filter`가 가장 중요하다. ON은 가치를 즉시 전달하지만 사용자가 직접 켠 신호를 잃는다. OFF는 토글 클릭이 곧 의도 신호라 데이터 품질이 높지만 가치 전달이 늦다. 표본이 작을 것이므로 불균형 배정은 쓰지 않고 50 대 50으로 간다.

### 6.9 개인정보 처리

> 11절(2026-10-02 개정)이 이 절을 보완하고 일부 대체한다. 동의와 최소 수집은 11절을 따른다.

- 리뷰 본문은 앰플리튜드로 보내지 않는다. `review_id_hash`만 보낸다
- 이메일은 해시해서 `user_id`로만 쓴다
- 확장이 읽은 페이지 내용은 어떤 형태로도 서버에 저장하지 않는다
- 랜딩에 개인정보 처리 방침을 게시한다

계측 과정에서 개인정보 경계를 어디에 뒀는지 설명할 수 있다는 점 자체가 포트폴리오 가치를 가진다.

### 7.1 채널

PC 사용 비중이 높고 쇼핑 정보에 민감한 커뮤니티를 우선한다. 확장은 PC 전용이므로 채널 선택이 표본 규모를 직접 결정한다.

### 7.2 표본 목표

```
방문 5,000  ×  PC 비중 40%  ×  설치 전환 8%  =  약 160명
```

퍼널 분석이 성립하는 최소 규모는 설치 50에서 100명이다. 채널을 잘 고르면 달성 가능하다.

확장 사용자가 상품을 볼 때마다 체험단 비율 데이터가 쌓인다. 일정 기간 후 집계를 공개한다.

> 사용자들이 확인한 상품 1,200개를 분석했습니다. 체험단 비중이 높은 카테고리는...

수집 노동 없이 콘텐츠가 생기고, 그 콘텐츠가 다시 유입을 만든다. 상품 단위 집계만 사용하고 개인의 열람 이력은 다루지 않는다.

## 11. 개정: 동의와 최소 수집 (2026-10-02)

이 절은 앞의 절과 충돌하면 앞의 절을 대체한다. 대체하는 곳: 3.1(온보딩), 6.1(신원 연결), 6.2(`product_id`), 6.3(`Extension Installed`, `page_first_review_id`), 6.9(개인정보 처리).

### 11.1 왜 바꾸는가

웹스토어 제출을 준비하며 크롬 웹스토어 사용자 데이터 정책을 확인했다.

- 웹 브라우징 활동(사용자가 요청하거나 상호작용한 웹 자원에 관한 모든 정보)의 수집은 스토어 설명과 제품 화면에 눈에 띄게 설명된 사용자용 기능에 필요한 범위에서만 허용된다
- 분석 데이터는 기능을 유지하고 성능과 안정성을 측정하는 데 필요한 만큼만 허용되고, 일반적인 시장 조사는 허용되지 않는다
- 수집 전에 제품 화면 안에서 눈에 띄게 알리고 사용자의 명시적 동의를 받아야 한다. 개인정보 처리방침이나 스토어 설명만으로는 부족하다

기존 설계는 설치 즉시 쿠팡 상품 번호와 구매 버튼 클릭을 동의 없이 보냈다. 정책에 맞지 않고, 정책이 없더라도 옳지 않다.

### 11.2 동의

- 설치 직후 확장 안의 온보딩 페이지(확장 내부 페이지)가 열린다. 무엇을 보내고 무엇을 보내지 않는지 보여 주고 `동의하고 시작`, `통계 없이 사용` 중 하나를 고르게 한다
- 동의 상태는 `granted`, `denied`, `undecided`(아직 고르지 않음) 셋이다. **`granted` 일 때만 이벤트를 보낸다.** 그 밖에는 아무것도 보내지 않고 쌓아 두지도 않는다
- 사이드 패널에서 언제든 켜고 끌 수 있다. 패널의 `보내기` 는 다시 알리지 않고 바로 켜므로, 이미 고른 상태(`granted`, `denied`)의 동의 구역에 `보내는 내용 보기` 링크를 두어 온보딩 페이지를 연다. 아직 고르지 않은 상태에서는 `자세히 보고 고르기` 버튼이 같은 페이지를 연다
- 온보딩 페이지는 이미 고른 사용자에게 완료 화면을 그린다. 완료 화면에도 선택 화면과 같은 "보내는 것", "보내지 않는 것" 목록과 보충 설명을 보여 준다. 순서는 완료 문구, 예시 링크(`show` 변형만), `설정 바꾸기` 버튼, 구분선, 소제목 `보내는 내용`, 두 목록, 보충 설명, 처리방침 링크(있을 때만)다
- 한 번이라도 동의한 사용자에게는 사이드 패널 동의 구역 맨 아래에 익명 기기 번호를 보여 준다. 이미 보낸 통계의 삭제를 요청할 때 이 번호로 대상을 찾는다. 동의한 적이 없으면 보낸 통계가 없으므로 보여 주지 않는다. 번호는 화면에만 보이고 이벤트나 주소에 새로 실리지 않는다. 백그라운드는 이 번호를 확장 페이지(패널, 온보딩)가 물을 때만 돌려준다. 콘텐츠 스크립트가 동의 상태를 물으면 상태만 주고 번호는 주지 않는다
- 확장의 기능(배지, 숨기기, 배너, 패널)은 동의와 무관하게 전부 동작한다
- 실험 배정(화면 문구, 필터 기본값)은 동의와 무관하게 적용된다. 화면이 달라질 뿐 기록은 동의한 사용자에게서만 남는다

### 11.3 최소 수집

- 쿠팡 상품 번호 원문을 보내지 않는다. 설치마다 무작위로 만든 솔트와 함께 SHA-256 으로 바꾼 값의 앞 16자리(`product_key`)만 보낸다. 솔트는 기기를 떠나지 않으므로 받은 쪽은 원래 번호로 되돌릴 수 없고, 다른 사용자의 같은 상품과도 이을 수 없다
- 리뷰 번호(`page_first_review_id`)도 같은 방식으로 `page_key` 로 바꾼다
- 6.2 의 `product_id` 는 `product_key` 로, 6.3 의 `page_first_review_id` 는 `page_key` 로 읽는다
- 잃는 것: 상품의 카테고리나 가격대를 나중에 붙여 분석할 수 없다. 여러 사용자가 본 같은 상품을 하나로 합칠 수 없다. 4.4절 분석은 (기기, `product_key`, 정렬)의 첫 페이지를 단위로 하므로 그대로 가능하다
- 제거 주소(uninstall URL)에 기기 번호와 설치 시각을 싣는 것도 동의한 경우만이다. 쿼리가 아니라 조각에 싣는다: `<사이트 주소>/uninstalled?v=<버전>#d=<기기 번호>&i=<설치 시각>`. 조각은 서버로 전송되지 않으므로 호스팅 서버의 접속 기록에 기기 번호가 남지 않는다. 버전(`v`)은 식별자가 아니므로 쿼리에 둔다. 미동의면 조각이 없다
- 제거 안내 페이지는 조각에서만 `d` 와 `i` 를 읽고(쿼리의 `d`, `i` 는 읽지 않는다) 읽은 직후 주소창에서 조각을 지운다. 이 페이지가 보내는 이벤트는 세션 밖(`session_id` -1)으로 보내 제거 한 건이 세션 하나로 세어지지 않게 한다
- 오류 이벤트(`Extension Error`)에 예외 메시지 원문(`error_message`)을 싣지 않는다. 자유 텍스트에는 리뷰 내용이나 쿠팡 번호가 섞일 수 있다. `error_type` 과 `error_name` 만 보낸다. 콘텐츠 스크립트가 싣지 않고, 백그라운드도 이 키가 오면 지운다(두 겹)
- `error_name` 은 영문자만 1~40자일 때만 그대로 보내고 그 밖에는 `Unknown` 으로 바꾼다. 예외의 이름도 길이와 문자에 제한이 없는 문자열이기 때문이다. 콘텐츠 스크립트에서 한 번, 백그라운드에서 한 번 더 본다

### 11.4 이벤트 의미 변화

- `Extension Installed` 는 설치 순간이 아니라 **처음 동의한 순간**에 한 번 보낸다. 프로퍼티 `consent_source`(`onboarding` / `panel`), `seconds_since_install`
- `Extension Installed` 의 이벤트 시각은 보낸 시각이 아니라 동의를 저장한 시각이다. `seconds_since_install` 도 그 시각까지로 센다. 동의 직후 온보딩 페이지가 보내는 `Onboarding Viewed` 보다 늦게 찍히지 않아야 퍼널 `Extension Installed → Onboarding Viewed` 가 맞게 집계된다. 시각 지정은 백그라운드 내부에서만 하고, 페이지나 콘텐츠 스크립트가 보낸 이벤트는 시각을 지정할 수 없다
- 동의율은 이벤트로 잴 수 없다(거절한 사용자는 아무것도 보내지 않는다). 웹스토어 대시보드의 설치 수 대비 `Extension Installed` 수로 추정한다
- 분석의 표본은 동의한 사용자로 한정된다. 결과를 쓸 때 이 선택 편향을 명시한다
- 새 이벤트: `Onboarding Viewed`, `Onboarding Example Clicked`(확장 온보딩 페이지에서, 동의 후에만)
- `Onboarding Viewed` 의 프로퍼티 `example_shown`(boolean): 그 페이지 로드에서 변형상 예시 링크를 보여 주는지
- 6.8 의 `exp_onboarding_example` 은 확장 온보딩 페이지에서 수행한다
- 예시 링크는 선택을 마친 완료 화면(동의든 거절이든)에서만 보여 준다. 위치는 완료 문구 아래, `설정 바꾸기` 버튼 위다. 선택 전 화면과 `설정 바꾸기` 로 돌아온 선택 화면에는 없다. 선택 전에 보여 주면 링크를 눌러 떠난 사용자가 동의하지 않은 채 표본에서 빠져 실험이 치우친다. `show` 변형일 때만 보이고 변형을 모르면 숨긴다. 클릭은 화면의 동의 상태가 `granted` 일 때만 기록한다

### 11.5 신원 연결

> 12.2절(2026-10-03 개정)이 이 절의 후보안을 대체한다. 사람 단위로 잇지 않고 집계 수준으로 잇는다.

6.1 의 방식(랜딩의 `/installed` 페이지에서 콘텐츠 스크립트가 랜딩 `device_id` 를 받아 확장에 저장)은 쓰지 않는다. 랜딩 출처에 콘텐츠 스크립트를 붙이면 확장의 접근 범위가 쿠팡 밖으로 넓어지고, 기기 번호를 바꾸면 실험 배정이 다시 계산된다.
랜딩과 확장을 잇는 방법은 랜딩 계획(3b)에서 다시 설계한다. 동의한 사용자에 한해 확장이 랜딩의 한 페이지를 기기 번호와 함께 여는 방식을 후보로 둔다.

### 11.6 사용 목적의 한계

수집한 통계는 이 확장이 제대로 동작하는지, 어떤 화면이 사용자에게 더 도움이 되는지 확인하는 데 쓴다. 광고, 판매, 제3자 제공에 쓰지 않는다. 개인을 알 수 없는 집계 결과(예: 정렬별 체험단 비중)는 공개할 수 있으며 이 점을 동의 화면과 처리방침에 적는다.

## 12. 개정: 랜딩 (2026-10-03)

이 절은 앞의 절과 충돌하면 앞의 절을 대체한다. 대체하는 곳: 3.4(모바일), 5.3(랜딩 페이지), 6.1과 11.5(신원 연결), 6.2(`is_extension_installed`, `platform`, `entry_source`), 6.3(랜딩 이벤트), 6.6(F1), 6.8(`exp_install_cta`).

### 12.1 범위

- 랜딩은 사이트의 첫 화면(`/`) 한 페이지다. 확장 패키지는 바꾸지 않는다. 재심사가 없다
- 서버 함수를 만들지 않는다. 이메일을 받지 않는다
- 만들지 않는 것: 이메일 핸드오프, `is_extension_installed`(확장이 랜딩에 표식을 심어야 해서 확장의 접근 범위가 쿠팡 밖으로 넓어진다), `Share Clicked`(넘기기 버튼과 겹친다)

### 12.2 신원 연결: 집계 수준

- 랜딩 방문자와 확장 설치자를 사람 단위로 잇지 않는다. 랜딩은 자기 방문자 번호를, 확장은 자기 기기 번호를 쓰고 둘을 짝짓는 이벤트는 없다
- 획득 퍼널은 숫자끼리 잇는다: 랜딩의 이벤트 수, 웹스토어 대시보드의 설치 수, 확장의 `Extension Installed` 수(동의자)
- 스토어로 가는 링크에 UTM(유입원, 실험 변형)을 싣는다. 대시보드가 UTM 별 설치 수를 보여 주면 채널별, 변형별 설치를 집계로 본다. 보여 주지 않으면 설치 수는 전체 합계로만 쓴다
- 이유: 목표 표본이 설치 50~160명이라 채널별로 나누면 칸마다 20~30명이고 사람 단위로 이어도 판독할 수 있는 것이 적다. 사람 단위 연결은 확장이 랜딩을 기기 번호와 함께 여는 변경이 필요해 재심사와 고지 추가가 따른다
- 보류: 다른 이유로 확장을 다시 제출하게 되면 그때 사람 단위 연결(동의한 사용자에 한해 확장이 랜딩의 한 페이지를 기기 번호를 조각에 실어 여는 방식)을 함께 넣을지 다시 정한다
- 제거 안내 페이지는 지금처럼 확장의 기기 번호만 쓴다. 랜딩 방문자 번호를 읽지 않는다

### 12.3 화면

- 첫 화면은 PC 에서 좌우 2단이다. 왼쪽에 문장, 보조 문장, 설치 버튼. 오른쪽에 예시 평점 카드(`쿠팡 평점 4.7 → 4.1`, `예시` 표기). 좁은 화면에서는 카드가 위, 문장과 버튼이 아래로 쌓인다
- 예시 카드는 사진이 아니라 페이지의 글과 스타일로 그린다. 숫자가 예시임을 카드 안에 적는다
- 그 아래: 실제 화면 사진, 기능 세 가지(표시, 숨기기, 뺀 평점), 보내는 것과 보내지 않는 것 요약, 처리방침 링크, 쿠팡과 관계없는 개인 도구라는 문장
- 명세 4.4절의 관측(정렬별 체험단 비중)은 랜딩에 쓰지 않는다. 상품 하나의 관측이고, 검증 전 주장으로 설치를 유도하면 표본이 그 주장에 끌린 사람으로 치우친다
- 사진에는 리뷰어 이름(가려진 이름 포함), 상품 이름, 리뷰 본문이 읽히지 않아야 한다
- 색과 글꼴은 기존 사이트(`site/public/style.css`)의 것을 쓴다. 원격 글꼴과 원격 자원을 불러오지 않는다
- 스토어 공개 전(`STORE_LIVE = false`)에는 설치 버튼과 따라오는 설치 바 대신 `크롬 웹스토어 심사 중입니다. 곧 설치할 수 있어요` 를 보여 준다

### 12.4 모바일: 이메일 없는 넘기기

- 모바일로 판정한 방문자에게는 설치 버튼 대신 `PC 크롬에서 설치할 수 있어요` 와 `링크 복사`, `공유하기` 버튼을 보여 준다. `공유하기` 는 브라우저가 공유 기능을 지원할 때만 보인다
- 넘기는 주소: `<사이트 주소>/?utm_source=handoff&utm_medium=<copy|share>&utm_campaign=<원래 유입원>`. 원래 유입원을 실어야 넘겨받은 방문을 처음의 채널로 되돌려 셀 수 있다. 유입원이 도메인이면 점을 `-` 로 바꿔 싣는다(`clien.net` → `clien-net`). 받는 쪽의 UTM 검증을 통과해야 하기 때문이다. 유입원이 `internal` 이면 싣지 않는다
- 넘겨받은 PC 방문은 `utm_source=handoff` 인 `Landing Viewed` 로 센다. 넘긴 사람과 연 사람이 같은지는 알 수 없고 수만 센다

### 12.5 랜딩 계측

**방문자 번호**

- 무작위 UUID 를 `localStorage` 의 `crf_site_device_id` 에 보관한다(지속). 동의 배너는 두지 않고 처리방침에 적는다
- `localStorage` 를 쓸 수 없으면 그 페이지 로드에서만 쓰는 번호를 만든다. 페이지는 그대로 동작한다
- 주소에 `#notrack` 을 붙여 한 번 열면 그 브라우저는 이후 계측에서 빠진다(`crf_site_optout`). `#track` 으로 되돌린다. 방문자가 통계에서 빠지는 방법이자 만든 사람의 방문을 빼는 방법이다
- 자동화 브라우저(`navigator.webdriver`), 검색 로봇류(UA 에 `bot`, `crawl`, `spider`, `headless`, `lighthouse`), 보이지 않는 상태로 미리 그려진 페이지는 기록하지 않는다. 브라우저 종류를 보내지 않으므로 나중에 걸러 낼 수 없다
- 운영 주소(`crf-review-remover.vercel.app`)가 아닌 곳(미리보기 배포, 로컬)에서는 보내지 않는다. 계측 제외 설정은 주소마다 따로라 미리보기 주소에서는 이어지지 않는다

**공통 프로퍼티**

| 프로퍼티 | 값 |
|---|---|
| `surface` | `site` |
| `device_class` | `desktop` / `mobile`. 아이패드(맥 UA + 터치)와 안드로이드 태블릿은 `mobile`. 데스크톱 모드를 켠 태블릿은 구분할 수 없어 `desktop` 으로 남는다 |
| `entry_source` | 유효한 `utm_source` 가 있으면 그 값, 없으면 유입 도메인(자기 사이트면 `internal`), 그것도 없으면 `direct`. 처리방침과 제거 페이지가 `no-referrer` 라 지금은 `internal` 이 나오지 않는다 |
| `exp_install_cta` | `hero_only` / `hero_sticky` / `none`(모바일) |
| `store_live` | boolean. 스토어 공개 전 방문을 분석에서 빼는 데 쓴다 |
| `id_persisted` | boolean. 방문자 번호를 브라우저에 저장했는지. false 면 로드마다 새 번호라 방문자 수 계산에서 뺀다 |

최상위 `platform` 은 기존 사이트 이벤트와 같이 `Web` 이다. `session_id` 는 페이지 로드 시각이다.

**이벤트**

| 이벤트 | 프로퍼티 | 때 |
|---|---|---|
| `Landing Viewed` | `referrer_domain`, `utm_source`, `utm_medium`, `utm_campaign` | 페이지 로드마다 한 번 |
| `Demo Viewed` | 없음 | 실제 화면 사진 구역의 위쪽 끝이 화면 세로 가운데까지 올라왔을 때, 페이지 로드마다 한 번. 구역의 높이와 화면 크기에 좌우되지 않게 보이는 비율로 정하지 않는다 |
| `Install CTA Clicked` | `cta_location`(`hero` / `sticky`) | 설치 버튼을 누를 때마다. 가운데 버튼 클릭도 센다. 우클릭 메뉴의 새 탭 열기는 잡을 수 없다 |
| `Handoff Link Requested` | `channel`(`copy` / `share`) | 넘기기 버튼을 누를 때마다 |

- `Store Redirected` 는 만들지 않는다. 설치 버튼이 일반 링크라 누름과 이동이 같은 사건이다
- `Handoff Link Opened` 는 만들지 않는다. `utm_source=handoff` 인 `Landing Viewed` 가 대신한다
- 최소 수집: 유입은 도메인만 보낸다(전체 주소와 경로를 보내지 않는다). UTM 값은 영문자, 숫자, `_`, `-` 로 된 1~40자만 소문자로 바꿔 받고 그 밖에는 버린다. 주소의 다른 쿼리와 조각은 읽지 않는다
- 공통 프로퍼티는 이벤트 프로퍼티가 덮어쓸 수 없다

### 12.6 실험 `exp_install_cta`

- 2종: `hero_only`(첫 화면 버튼만), `hero_sticky`(첫 화면 버튼 + 첫 화면 버튼이 화면 밖으로 나가면 화면 아래에 따라오는 설치 바). PC 방문자만 50 대 50 으로 배정하고 모바일은 `none` 이다
- 배정은 첫 방문 때 무작위로 정해 `localStorage` 의 `crf_site_exp_install_cta` 에 보관한다. 다시 와도 같은 변형이다
- 주 지표: `Landing Viewed` 가 있는 방문자 중 `Install CTA Clicked` 가 있는 방문자의 비율. 배정 기준으로 읽는다(설치 바를 실제로 봤는지로 나누지 않는다)
- 3종에서 2종으로 줄인 이유: PC 방문 목표가 2,000명 안팎이라 3종이면 칸당 약 670명이다. 2종이면 칸당 약 1,000명이고 클릭률 15% 기준 5%p 안팎의 차이부터 판독할 수 있다
- 분석 조건: `store_live = true`, `device_class = desktop`. 스토어 공개 전의 방문은 버튼이 없었으므로 뺀다

### 12.7 획득 퍼널 F1 (집계)

`Landing Viewed` → `Install CTA Clicked` → 웹스토어 설치 수(대시보드) → `Extension Installed`(동의자).

앞의 두 칸은 방문자 단위, 뒤의 두 칸은 합계다. 칸 사이의 비율은 같은 기간의 합계로 계산하고, 사람 단위 전환율이 아님을 결과에 적는다. 모바일은 따로 본다: `Landing Viewed`(mobile) → `Handoff Link Requested` → `Landing Viewed`(`utm_source=handoff`).

### 12.8 개인정보

- 처리방침에 랜딩 방문 통계 절을 넣는다: 무작위 방문자 번호, 유입 도메인, 광고 표식(UTM), 화면 종류, 누른 버튼, 실험 그룹. 통계에서 빠지는 방법(`#notrack`, 사이트 데이터 삭제)
- 이름, 이메일, 전체 주소를 다루지 않는다
- 앰플리튜드가 접속 IP 로 무엇을 남기는지는 실제 이벤트로 확인한 뒤 처리방침 5절의 문구를 정한다(계획 3a 의 보류 항목)
- 처리방침을 고칠 때마다 확장의 실제 동작과 계속 일치하는지 대조한다

## 13. 개정: 무신사 지원 (2026-10-08)

이 절은 앞의 절과 충돌하면 앞의 절을 대체한다. 대체하는 곳: 이름(`체험단 리뷰 제거기 for 쿠팡`), 5.2(권한), 6.2(공통 프로퍼티에 `site` 추가, `review_sort` 의 값), 11.2(동의의 범위), 부록의 "플랫폼: 쿠팡 단일".

계기와 확인 결과는 `docs/research/2026-10-07-other-stores.md` 에 있다. 부트캠프 슬랙에서 "무신사와 올리브영에서도 쓸 수 있으면 좋겠다" 는 피드백을 받았다. 무신사는 체험단 후기에 표시를 붙이지만 빼고 보는 방법이 없다(체험단 탭은 모아 보기다). 쿠팡과 조건이 같다. 올리브영은 체험단 표시를 찾지 못해 넣지 않는다.

### 13.1 범위

- 지금 확장에 무신사를 더한다. 버전 1.1.0. 따로 확장을 만들지 않는다
- 이름을 `체험단 리뷰 제거기` 로 바꾼다. 지원하는 쇼핑몰은 요약과 설명에 적는다. `short_name` 과 툴바 제목은 그대로다
- 무신사에서 동작하는 페이지: 상품 페이지(`www.musinsa.com/products/<번호>`), 후기 전체보기(`www.musinsa.com/review/goods/<번호>`). 후기 전체보기는 13.10 의 실브라우저 확인에서 숨김이 깨지면 1.1.0 에서 뺀다
- 쿠팡 쪽의 동작은 바꾸지 않는다
- 하지 않는 것: 올리브영, 무신사의 후기 목록 주소를 확장이 직접 부르는 것, 무신사 모바일 앱과 모바일 웹, 무신사의 스냅과 스타일 후기, 4.4절 분석을 무신사로 넓히는 것

### 13.2 판별과 계산

- 판별 원칙은 4.1절과 같다. 쇼핑몰이 직접 붙인 문구만 본다. 무신사의 문구는 `이 후기는 제품을 무상으로 제공받아 직접 사용해 본 후 작성되었습니다.` 이고 앞부분 `이 후기는 제품을 무상으로 제공받아` 를 기준으로 삼는다. 공백은 무시하고 비교한다
- 쿠팡의 문구는 쿠팡 페이지에서만, 무신사의 문구는 무신사 페이지에서만 본다
- 후기 번호: 후기 카드의 `data-content-id`(숫자). 숫자가 아닌 값은 후기 카드가 아니다(같은 속성을 메뉴와 요약 구역도 쓴다)
- 별점: 후기 카드에 숫자(1~5)로 적혀 있다(13.8). 1~5 의 정수가 아니면 그 카드는 세지 않는다
- 계산 범위는 쿠팡과 같다. 화면에 나온 후기를 번호로 누적해 체험단 비중과 체험단을 뺀 평점을 낸다. 상품 전체의 통계가 아니라는 안내도 같다
- 무신사 상품 페이지 위쪽의 공식 평점(예: 4.9)은 읽지 않는다. 배너의 "리뷰 평균" 은 쿠팡과 같이 본 후기의 평균이다

### 13.3 무신사에서만 다른 동작

- **체험단 탭.** 사용자가 무신사의 `체험단` 탭을 고르면 화면의 후기가 전부 체험단이다. 이 탭이 선택된 동안에는 숨기지 않는다. 표시(배지)는 붙이고 배너는 숨김 버튼 대신 `체험단 후기만 모아 보는 중입니다` 를 보여 준다. 탭에서 나오면 원래 상태(숨김 설정)로 돌아간다. 이 탭에서 본 후기도 누적에는 넣는다(번호로 중복을 거르므로 두 번 세지 않는다)
- 무신사의 다른 탭(`일반`, `뷰티`, `한달후기`)과 조건(성별, 구매옵션, 사진후기만)은 구분하지 않는다. 쿠팡에서 별점 조건을 구분하지 않는 것과 같다
- **화면만 바꾸는 이동.** 무신사는 페이지를 새로 불러오지 않고 주소와 화면만 바꿀 수 있다. 주소가 바뀌면 상품 번호를 다시 읽고 누적을 새로 시작한다. 대상 페이지가 아닌 주소에서는 아무것도 하지 않고 배너도 지운다
- **구매 버튼.** `장바구니`, `구매하기` 를 쿠팡의 `cart`, `buy_now` 와 같은 값으로 기록한다
- **숨기는 방식.** 무신사에서는 카드를 없애지 않고 높이 1px 로 접는다. 후기 전체보기의 목록은 화면 밖 카드를 지우고 카드 높이를 재서 자리를 잡는데, 높이가 0 인 카드는 그 계산을 깨뜨릴 수 있다. 상품 페이지에서도 같은 방식을 쓴다. 쿠팡은 지금처럼 없앤다
- **정렬.** `review_sort` 에 무신사의 정렬을 적는다. `유용한순` 은 `useful`, `최신순` 은 `latest`, `댓글순` 은 `comments`, `높은 평점순` 은 `rating_high`, `낮은 평점순` 은 `rating_low` 이고 읽지 못하면 `unknown` 이다. 쿠팡의 `best` 와 무신사의 값은 뜻이 다르므로 정렬 분석은 쇼핑몰별로 따로 한다

### 13.4 구조

- 쇼핑몰마다 다른 부분을 "쇼핑몰별 부품" 으로 뗀다. 부품 하나가 정하는 것: 어느 주소가 대상 페이지인지와 상품 번호, 후기 구역과 후기 카드를 찾는 법, 후기 번호와 별점과 글을 읽는 법, 체험단 문구, 정렬을 읽는 법, 구매 버튼, 배너를 넣을 자리, 숨기면 안 되는 상태인지(무신사의 체험단 탭)
- 누적, 평점 계산, 배지, 숨김, 배너, 패널, 건강 신호, 통계 전송은 공통이고 부품을 받아서 쓴다
- 쿠팡 부품은 지금 코드를 옮긴 것이다. 옮기기 전의 테스트가 고치지 않은 채로 통과해야 한다
- 건강 신호(`ReviewContainerNotFound`, `ReviewRatingNotFound`, `ReviewIdNotFound`)는 무신사에도 같은 뜻으로 쓴다. 후기 구역이 화면 어디쯤에 있는지가 달라 임계값은 부품이 정한다

### 13.5 계측

- 공통 프로퍼티 `site` 를 더한다: `coupang` / `musinsa`. 콘텐츠 스크립트가 보내는 모든 이벤트에 붙는다. 사이드 패널 이벤트에는 그 탭의 요약에 적힌 쇼핑몰을 싣고, 요약이 없으면 `unknown` 이다. 온보딩과 설치, 제거 이벤트에는 붙지 않는다
- 1.1.0 전의 이벤트에는 `site` 가 없다. 분석에서는 `app_version` 이 1.1.0 미만이면 `coupang` 으로 읽는다
- `product_key`: 쿠팡은 지금처럼 상품 번호만으로 만든다(이미 보낸 값과 이어진다). 무신사는 `musinsa:<번호>` 로 만든다. 두 쇼핑몰의 번호가 같아도 값이 겹치지 않는다. `page_key` 도 같다
- 이벤트 이름과 프로퍼티의 뜻은 그대로다. 실험 배정(`exp_default_filter`, `exp_banner_copy`)은 기기 단위이므로 두 쇼핑몰에서 같은 변형이다
- 북극성과 퍼널, 가드레일은 쇼핑몰을 합쳐서 보고 `site` 로 나눠서도 본다. 4.4절(정렬별 체험단 비중)은 `site = coupang` 만 쓴다
- **무신사의 관측 단위.** 쿠팡의 `Banner Rendered` 는 리뷰 페이지를 넘길 때마다 한 번이다. 무신사는 페이지가 없고 후기 전체보기는 스크롤할 때마다 화면의 카드가 한두 장씩 바뀐다. 그래서 무신사에서는 상품에서 처음 후기를 읽었을 때 한 번, 그 뒤로는 새로 본 후기가 10개 쌓일 때마다 한 번 보낸다. `pages_seen` 은 이 횟수다. `page_review_count`, `page_sponsored_count`, `page_key` 는 그 순간 화면에 있던 카드의 값이라 무신사에서는 페이지 단위 분석에 쓰지 않는다. 누적 값(`review_count`, `sponsored_ratio`, 평점)은 쿠팡과 같은 뜻이다
- 새 프로퍼티: `Banner Rendered` 에 `sponsored_only_view`(boolean). 무신사의 체험단 탭에서 그린 배너다. 이때의 체험단 비중은 탭이 고른 결과라 비중 분석에서 뺀다

### 13.6 권한과 동의

- 콘텐츠 스크립트의 대상에 `https://www.musinsa.com/products/*` 와 `https://www.musinsa.com/review/goods/*` 를 더한다. 무신사 전체를 대상으로 잡지 않는다. 실측에서 랭킹의 상품 링크와 상품 페이지의 후기 전체보기 링크가 모두 새 탭으로 열렸다(새로 불러온다). 다른 경로로 화면만 바뀌어 들어온 경우에는 새로 고칠 때까지 동작하지 않는다. 권한을 좁게 두는 쪽을 골랐다
- 대상 사이트가 늘면 크롬은 기존 설치자의 확장을 끄고 새 권한을 허용할지 묻는다. 지금 설치자가 거의 없어서 홍보로 늘기 전에 한다
- **동의를 다시 받는다.** 1.0.x 에서 한 동의는 "쿠팡 상품 페이지" 를 알리고 받은 것이다. 1.1.0 으로 올라온 기기의 동의 상태가 `granted` 면 `undecided` 로 되돌리고 온보딩 페이지를 한 번 연다. `denied` 와 `undecided` 는 그대로 두고 페이지도 열지 않는다. 기기 번호, 설치 시각, 실험 배정은 그대로다
- 다시 동의하면 `Extension Installed` 를 또 보내지 않는다(기기당 한 번). 대신 그 시점부터 이벤트가 다시 나간다
- 온보딩과 패널의 "보내는 것" 목록에서 `쿠팡` 을 `쿠팡과 무신사` 로 고친다

### 13.7 고칠 글

| 곳 | 고칠 것 |
|---|---|
| 매니페스트 | 이름, 요약(`쿠팡과 무신사의 리뷰에서 ...`), 버전 1.1.0 |
| 온보딩, 사이드 패널 | 쇼핑몰 이름이 들어간 문장. 예시 링크는 쿠팡 상품 그대로 |
| 스토어 등록 자료 | 이름, 설명, 단일 목적, 권한 사유, 심사자 안내에 무신사 예시 주소, 스크린샷에 무신사 화면 한 장 |
| 처리방침 | 대상 사이트, 수집 항목의 쇼핑몰 구분, 시행일. 확장의 실제 동작과 대조한다 |
| 랜딩 | 제목과 예시 카드는 쿠팡 그대로 두고 `무신사에서도 동작합니다` 한 줄을 더한다. 랜딩 계측은 바꾸지 않는다 |

`쿠팡과 관계없는 개인이 만들었다` 는 뜻의 문장은 모든 곳에서 무신사도 함께 적는다.

### 13.8 실측 결과 (2026-10-08)

크롬 헤드리스로 로그인하지 않은 상태에서 상품 4633343 의 상품 페이지와 후기 전체보기를 열어 확인했다. class 이름 뒤의 꼬리(`-sc-...`)는 바뀔 수 있어 앞부분만 쓴다.

| 항목 | 결과 |
|---|---|
| 후기 카드 | `[data-section-name="review"][data-content-id]`. `data-content-id` 만으로는 부족하다(매거진 카드도 숫자 값을 쓴다) |
| 후기 구역 | `[class*="GoodsReviewListSection__Container"]`. 탭, 조건, 정렬, 목록을 담는다. 두 페이지에 모두 있다 |
| 별점 | 카드 안 `[class*="StarsScore__Container"]` 의 글자(숫자 하나) |
| 체험단 문구 | 카드 안 `[class*="ExperienceLabelInfo__Wrapper"]` 에 `체험단` 과 `이 후기는 제품을 무상으로 제공받아 직접 사용해 본 후 작성되었습니다.` 가 들어 있다. 사용자가 쓴 글이 아니라 화면 부품이라 문구가 하나다 |
| 체험단 조건 | `[data-filter-value="체험단"]`. 고르면 class 에 `border-black` 이 붙고 고르지 않으면 `border-gray-300` 이다. 다른 속성은 달라지지 않는다 |
| 정렬 | `[data-filter-type="array_click"]` 의 글자가 지금 정렬이다. 메뉴의 항목은 유용한순, 최신순, 댓글순, 높은 평점순, 낮은 평점순 |
| 구매 버튼 | `[data-button-id="basket_btn"]`(장바구니), `[data-button-id="2depth_buy_btn"]`(구매하기) |
| 상품 페이지의 목록 | 고정 목록, 카드 10장. 문서 길이의 40% 쯤에 있고 스크롤해야 그려진다. 탭이나 조건을 바꾸면 10장이 바뀐다. 더 보려면 후기 전체보기(새 탭)로 간다 |
| 후기 전체보기의 목록 | 화면 밖 카드를 지우는 목록(`[data-testid="virtuoso-item-list"]`). 한 번에 5~6장만 있다. 페이지 번호는 없고 스크롤하면 이어진다 |
| 이동 | 랭킹의 상품 링크와 후기 전체보기 링크는 `target="_blank"` 다 |
| 로그인 | 필요 없다 |
| 창이 가려진 상태 | 후기 전체보기는 창이 보이지 않으면 카드를 그리지 않는다. 확장의 동작에는 영향이 없다 |

### 13.9 위험

- 무신사의 class 이름은 빌드마다 바뀔 수 있는 꼬리(`-sc-1eq1l6b-0`)가 붙는다. class 전체에 기대지 않고 `data-` 속성과 글자를 우선해서 읽는다
- 재심사가 처음보다 길어질 수 있다. 심사 중에도 1.0.0 은 게시된 채로 남는다
- 무신사에서 체험단 후기가 있는 상품은 뷰티 랭킹 40개 중 3개였다. 설치자가 무신사에서 배너를 볼 일이 쿠팡보다 드물 수 있다. 체험단이 0건인 상품에서의 배너 동작은 쿠팡과 같다
- 분석의 표본이 두 쇼핑몰로 나뉜다. 지금은 표본이 거의 없어 나뉘어도 잃는 것이 작고 `site` 로 다시 가를 수 있다
- 무신사가 후기 카드의 표식(`data-section-name="review"`)을 바꾸면 후기 구역은 찾는데 카드를 하나도 못 찾는다. 후기가 없는 상품과 구분되지 않아 건강 신호가 나가지 않는다. 13.10 의 확인 스크립트를 출시 뒤에도 가끔 돌려 본다

### 13.10 실브라우저 확인

- 일반 크롬은 명령줄로 확장을 싣는 것을 막는다. 그래서 빌드한 콘텐츠 스크립트와 스타일을 크롬 헤드리스의 무신사 페이지에 직접 넣고 `chrome.runtime` 을 흉내 내어 확인한다(`scripts/verify-musinsa.mjs`). 확인하는 것: 배너가 뜨는지, 체험단 카드에 표시가 붙는지, 숨기면 접히고 다시 보면 돌아오는지, 체험단 조건에서 숨기지 않는지, 후기 전체보기에서 숨긴 채 끝까지 스크롤해도 목록이 이어지는지, 보낸 이벤트의 `site` 와 횟수
- 동의 다시 받기, 권한 다시 묻기, 사이드 패널은 사용자가 실제 크롬에서 압축 해제된 확장으로 확인한다

**결과 (2026-10-08, 상품 4633343, 23개 항목 통과)**

- 상품 페이지: 카드 10장 중 체험단 2장에만 표시가 붙었다. 숨기면 두 장이 높이 1px 로 접히고 나머지는 576px 이상으로 남았다. 무신사의 체험단 조건을 고르면 접힌 카드 없이 10장이 보이고 배너에 안내 글이 떴다. 조건을 풀면 다시 접혔다
- 후기 전체보기: 숨김을 켠 채 끝까지 스크롤해 277장을 봤고 그중 체험단은 43장이었다. 배너의 누적 수와 페이지에서 따로 센 수가 같았다. 접힌 카드 때문에 목록이 멈추거나 튀지 않았고 높이 0 경고도 없었다. 그래서 후기 전체보기를 1.1.0 에 넣는다
- 이벤트: 전부 `site` 가 `musinsa`, `product_id` 가 `musinsa:4633343` 이었다. `Banner Rendered` 는 상품 페이지에서 누적 18건에 1번, 후기 전체보기에서 277건에 27번 나갔다
- 확인 중에 알게 된 것: 무신사는 스크롤할 때 카드 요소를 새로 만들지 않고 번호 속성만 바꿔 다시 쓰기도 한다. 확장은 277장을 모두 셌다(다른 변화가 함께 일어나 다시 읽는다)
